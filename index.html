Block 1 · What an agent is9 / 30

A chatbot advises. An agent acts.

The difference is not quality. It is who does the work.

A chatbot

Answers in sentences

  • You paste the code in
  • It describes the change
  • Nothing happens until you act
An agent

Changes the files

  • It reads the repository
  • It makes the change
  • It runs the tests
Takeaway

With a chatbot you check the advice. With an agent you check the work.

How you hand over a task

A vague request gets a vague result. That is true of people too.

The four lines of a brief

The same four lines you would give a new colleague on their first day.

LineAnswersExample
GoalWhat must be true at the end?"The rename is complete and tests pass."
ContextWhat does it need to know?"Three files use it; the API must not change."
ConstraintsWhat must it not touch?"Do not change the public signature."
Done whenHow will you both know?"Show me the test output, not a summary."
Takeaway

Miss the last line and you get prose instead of proof.

Block 2 · How you hand over a task15 / 30

"Fix the bug" versus a brief

What you said

"Fix the login bug"

  • It guesses which bugThere may be three
  • It guesses "fixed"No test named
  • It changes whatever it likesNo constraint
What you should say

A four-line brief

  • Goal: login accepts expired sessions
  • Context: see auth/session.ts
  • Constraint: no schema changes
  • Done: npm test auth passes
Takeaway

The brief is not politeness. It is how you make the result checkable.

Permissions and the trust dial

The most important setting isn't the model. It's what it may do without asking.

What it may do without asking

Two of the four levels. Described by behaviour, not by menu name.

Ask every time It proposes each change; nothing happens until you approve. Like signing every expense claim
Plan only It reads and drafts a plan; it changes no files. Like a quote before the work

These two are for work you want to see before it happens. The next two are for work you are willing to check afterwards.

Block 3 · Permissions and the trust dial21 / 30

What it may do without asking

The other two. Both write to your disk.

Edits without asking It writes files freely; running commands still needs you. Like a manager's approval limit
Full access It edits and runs anything in reach, unsupervised. Like handing over the keys
Takeaway

The dial is a business decision, written down before the work.

Block 3 · Permissions and the trust dial22 / 30

How to choose a level

The same test you already apply to a company card.

If a mistake…Then…Example
is cheap to undolet it actRenaming a variable across files
is caught on reviewlet it act, then read the diffRefactoring one module
cannot be undonea person decidesDeleting files, force-pushing, migrating data

The level follows the cost of a mistake, not the difficulty of the task.

Takeaway

Generous where it is reversible. A person wherever it is not.

Block 3 · Permissions and the trust dial23 / 30

Set the dial

In groups, 5 minutes. Take the brief you wrote in Block 2.

Use 1

Rename a variable

A mistake is one undo away. Where does acting without asking start?

Use 2

Refactor a module

Tests catch most mistakes. What still needs a person?

Use 3

Delete old files

No undo, no warning. Who says yes?

Takeaway

Write the three levels down before the session, not after the incident.

Block 3 · Permissions and the trust dial24 / 30

Where the room put the line

Groups that allowed

Cheap and reversible

Renames and formatting. Nobody wanted to review those.

Groups that hesitated

The review cost

Refactors were allowed — if someone read the diff.

Nobody allowed

Anything with no undo

Deleting, migrating, forcing. Every group kept a person there.

Takeaway

Reversibility decided it, not task difficulty — and not the model's confidence.

Block 3 · Permissions and the trust dial25 / 30

Four things that will bite

Confident, and wrong

It states success in the same tone whether it worked or not. Read the output.

Context runs out

Long sessions lose early detail. Start fresh for a new task.

It costs money

Every read and run spends tokens. Long loops add up. Watch the bill.

The change is real

Not a draft. A file on disk, a command that ran. Version control is your undo.

Takeaway

None of these are reasons not to use it. They are the checking you owe it.
